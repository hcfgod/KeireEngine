## One technical library

The website renders the maintained Markdown under `Docs/` directly into native documentation pages. Search, sidebars,
page outlines, code copy controls, and previous/next navigation work locally on this site; GitHub remains the source and
contribution workflow, not the reading experience.

## Find the right kind of guide

- **User manual:** follow a task, prepare its prerequisites, and check the expected result. Start here if you are
  making a game.
- **Technical references:** check an exact API, asset format, ownership rule, or failure boundary when a task needs
  more detail.
- **Design plans and acceptance records:** read dated proposals, comparisons, measurements, and remaining gates.
  These preserve engineering history; their old menu names are not current creation instructions.

New materials use the Inspector. The older `material-graph` address remains available so existing links keep working;
the page now teaches the current Materials workflow.

Before sharing or cleaning a project, read [Back Up, Share, and Recover a Project](/docs/reference/manual/project-maintenance/).
Before calling gameplay finished, use [Test Gameplay Before You Ship](/docs/reference/manual/gameplay-testing/).

<Aside type="caution" title="Kéire is pre-1.0">
  The documentation describes implemented repository behavior and calls out incomplete production-readiness work without
  invented dates or guarantees. Use [Current Acceptance Evidence](/docs/reference/current-acceptance-evidence/) to
  distinguish a source capability from a verified platform release. Dated readiness reviews retain their original scope.
</Aside>
