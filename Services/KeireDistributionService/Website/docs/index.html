Guide 01

Getting started

Kéire uses the repository launchers as the supported interface for dependency bootstrap, project generation, builds, tests, runs, packaging, and diagnostics. Clone submodules, then let the launcher validate the workstation.

Windows

git clone --recurse-submodules https://github.com/hcfgod/KeireEngine.git
cd KeireEngine
./Scripts/project.ps1 bootstrap -Generator vs2022
./Scripts/project.ps1 test -Generator vs2022 -Configuration Debug
./Scripts/project.ps1 run -Generator vs2022 -Configuration Debug

Linux or macOS

git clone --recurse-submodules https://github.com/hcfgod/KeireEngine.git
cd KeireEngine
bash Scripts/project.sh bootstrap --generator ninja --toolset clang
bash Scripts/project.sh test --generator ninja --configuration Debug --toolset clang
bash Scripts/project.sh run --generator ninja --configuration Debug --toolset clang

Run the launcher without a command for the interactive menu. Use doctor when a tool, compiler, SDK, or platform dependency is unclear.

Guide 02

Hub and editor

The Hub owns project discovery, templates, compatible editor selection, signed distribution catalogs, downloads, package tasks, and update handoff. Editors stay versioned and independent; project data is never owned by an installer.

Normal workflow

  1. Open Kéire Hub and create a project from a packaged template or register an existing project.
  2. Choose an installed editor compatible with that project schema.
  3. Launch the editor through the project entrypoint; the editor validates identity and acquires the exclusive project lock.
  4. Use Hub task and notification surfaces for installation, repair, Build Support, and update work.

The Hub can operate with installed content and last-known-good catalogs when offline. Account identity never substitutes for signed software-distribution trust.

Guide 03

Architecture

KeireCore contains reusable engine systems, KeireClient contains client and editor behavior, and test targets stay independent. Premake is the engine build authority; SDK CMake examples validate packaged consumers.

Core principles

  • Ownership is explicit through RAII, unique ownership, and engine reference-counted objects.
  • Application services and frame order have clear owners and deterministic safe boundaries.
  • Public headers remain free of private SDL, JSON, mutex, platform-handle, and implementation ownership.
  • Worker communication, asset publication, installs, and package release behave transactionally.
  • Platform-specific details remain behind guarded native boundaries.

The runtime runs layer updates bottom-to-top and events top-to-bottom. Structural mutations requested during traversal defer to the next safe boundary.

Guide 04

C# scripting

Managed gameplay assemblies build against the packaged .NET toolchain and Kéire API. Behaviour fields can participate in Inspector authoring while gameplay code reaches entities, assets, scenes, input, audio, animation, UI, physics, navigation, and other supported services.

Gameplay loop

  • Create managed Behaviours inside the project scripting layout.
  • Build through the editor so generated bindings, diagnostics, and assembly identity remain consistent.
  • Attach Behaviour types to entities and edit serializable fields through the Inspector.
  • Use Play Mode for runtime execution and supported reload paths.

Cooked players bind managed assembly roots and subsystem requirements into the runtime manifest. Incompatible or stale schema data fails with a direct recook diagnostic.

Guide 05

Rendering and materials

The renderer is application-owned and uses SDL_GPU while public runtime APIs stay backend-neutral. Host-side shader tooling produces target artifacts for DirectX, Vulkan, and Metal paths.

Authoring surface

  • Scene and Game views share validated cameras, lighting, mesh, material, and environment state.
  • Shader manifests declare sources, entry points, defines, reflection contracts, and supported features.
  • Material Graph uses a schema-versioned node catalog and validates generated variants before publication.
  • Render Graph and Architecture panels expose useful runtime structure without leaking private backend types.

GPU resources retire only after safe frame completion, while imported assets and generated shaders publish atomically into mounted catalogs.

Guide 06

Assets and player builds

Source assets receive stable metadata identity, import in isolated workers, and publish into validated development catalogs. Runtime handles resolve typed fallbacks immediately while asynchronous loads and reloads complete safely.

Release path

  1. Select a build profile and acquire compatible platform Build Support.
  2. Cook source content into deterministic runtime catalogs and packs.
  3. Assemble the native player with exact engine, module, platform, and architecture identity.
  4. Validate manifests, sizes, SHA-256 digests, licenses, launch behavior, and platform packaging.

Native editor and Hub installers remain separate. Online packages are immutable SHA-256 resources selected through exact-byte Ed25519-signed catalogs.
